## 3. ארכיטקטורת הפריסה — הכרעות

### הבנאי: Railpack (ולא Nixpacks או Dockerfile)
‏Railpack הוא ברירת המחדל הנוכחית של Railway (יורש Nixpacks, שנמצא במצב תחזוקה). הוא מזהה Next.js ובונה אותו נכון בלי תצורה — וזהו **משטח הסיכון הקטן ביותר שאי אפשר לאמת מקומית**. ‏Dockerfile היה נותן שליטה מלאה אך מעביר את כל הבנייה לאחריותנו, ללא יכולת לבדוק אותה בלי Docker במכונה (שאין). ‏Nixpacks היה מאפשר לקבע גרסת Postgres מדויקת אך סובל מעמימות במיזוג רשימות החבילות. הבחירה ב-Railpack משאירה את מלאכת Next+Prisma לפלטפורמה ומוסיפה רק את מה שחסר: לקוח Postgres.

### התלות הקריטית: התאמת גרסת pg_dump ↔ Postgres
ג'וב הגיבוי מריץ `pg_dump` בתוך הקונטיינר מול בסיס הנתונים של Railway. **‏pg_dump חייב להיות בגרסה ≥ גרסת השרת** — אחרת הוא מסרב לגבות. ‏`railpack.json` מתקין את `postgresql-client` בגרסת ברירת המחדל של בסיס הבנאי (‏Debian/Ubuntu, בדרך כלל 15–16). לכן:

> **חובה בזמן הפריסה:** ליצור את שירות ה-Postgres בגרסה ‏**16 או נמוכה יותר**, ולאמת בריצת הגיבוי הראשונה שאין שגיאת גרסה. אם הלוג מדווח שהלקוח ישן מהשרת — להוריד את `POSTGRES_VERSION` לגרסת הלקוח, או לעבור לגישת ה-Dockerfile (נספח §7).

זו אינה החלטה שאפשר "לנחש" מראש: היא מאומתת בפועל אחרי הפריסה. ראה [[node-tooling-on-this-machine]].

### מיגרציות: אוטומטיות ב-preDeployCommand
`prisma migrate deploy` רץ אוטומטית לפני כל עליית גרסה. אידמפוטנטי (מחיל רק מיגרציות שטרם הוחלו), אינו משתמש ב-shadow DB, ומתחבר דרך `DATABASE_URL` (ש-`prisma.config.ts` קורא). כשל עוצר את הפריסה — רצוי, כדי לא לעלות מול סכימה ישנה.

### פורט והרצה
‏`start:prod` = `next start` בלי `-p`, ולכן מאזין על `PORT` ש-Railway מזריק. אין להשתמש ב-`npm start` (נעול ל-3100).

### ⚠️ העובד (worker) — חובה שהקונטיינר יהיה תמיד־ער
ההסלמה היומית (06:00) והגיבוי הלילי (03:00) רצים בעובד **בתוך פרוסס השרת**, לא בשירות cron נפרד. אם מפעילים ב-Railway את **"App Sleeping" / Serverless**, הקונטיינר נרדם בחוסר תעבורה, העובד נעצר, והג'ובים הליליים לא ירוצו — כלומר הערך המרכזי של המערכת (התראה על פנייה תקועה) נשבר בשקט. **חובה להשאיר את App Sleeping כבוי.** ‏instance יחיד גם מבטיח שאין שני עובדים שמתנגשים על אותו ג'וב.

## 4. מדריך פריסה — שלב אחר שלב

> הפקודות הן ל-`railway` CLI (מותקן ומחובר). תחביר ה-CLI נוטה להשתנות בין גרסאות — לאמת מול `railway --help` בזמן הביצוע. יצירת שירותים אפשרית גם מה-Dashboard (לעיתים פשוט יותר), אך העדפת ה-CLI לפי הנחיות הפרויקט.

### 4.1 תשלום (החוסם)
לשדרג ל-Hobby ב-`railway.com/account/plans` (‏$5/חודש). ה-trial פג, ו-`railway init` ייכשל עד לשדרוג.

### 4.2 יצירת הפרויקט והשירותים
1. `railway login` — נפתח דפדפן לאישור.
2. `railway init` — יצירת פרויקט (או `railway link` לפרויקט קיים).
3. **שירות Postgres**: להוסיף מסד PostgreSQL. **לבחור גרסה 16 או נמוכה יותר** (ראה §3). לוודא שמשתנה `POSTGRES_VERSION` תואם.
4. **שירות ה-web**: זה ספריית הפרויקט. **מחובר לריפו הפרטי `harelfelhai/yy-ticket-control` ופורס אוטומטית על push ל-`main`** (‏Gate G7 אושר; ראו §4.6). ‏`railway up` עדיין אפשרי אך אינו בשימוש — הוא עוקף את גיט ומעלה את הקוד המקומי.

### 4.3 קישור בסיס הנתונים
להגדיר על שירות ה-web את המשתנה:
```
DATABASE_URL = ${{Postgres.DATABASE_URL}}
```
(‏reference variable — זמין גם בבנייה וגם בריצה. חייב להיות מוגדר **לפני** הבנייה, כי הקוד דורש שהמשתנה קיים.)

### 4.4 משתני סביבה
להגדיר את כל המשתנים מהטבלה ב-§5. **סודות מוגדרים ב-Railway Variables בלבד — לעולם לא בקוד ולא בגיט.** לא להזין סודות בצ'אט; אני מגדיר את שמות המשתנים, והערכים מוזנים על ידך ב-Dashboard/‏CLI.

### 4.5 כיבוי App Sleeping
לוודא בהגדרות שירות ה-web ש-**Serverless / App Sleeping כבוי** (ראה §3).

### 4.6 פריסה

**מ-15.8.2026 הפריסה אוטומטית.** שירות ה-web מחובר לריפו `harelfelhai/yy-ticket-control`,
וכל `git push` לענף `main` מפעיל בנייה ופריסה. **אין להריץ `railway up` ידנית** — הוא מעלה
את הקוד **המקומי**, כולל שינויים שלא נדחפו, ולכן יכול להעלות לאוויר מצב שאינו קיים באף קומיט.

הבנייה מריצה Railpack → `next build`; לפני העלייה לאוויר `preDeployCommand` מריץ
`npm run db:deploy` (מיגרציות), וה-healthcheck הוא `/login`.

## 6. פריטים פתוחים והחלטות

1. **התאמת גרסת Postgres ↔ pg_dump** (§3) — נקבעת ומאומתת בזמן הפריסה, לא לפני. פריט האימות הקריטי ביותר.
2. **פגיעות sharp (‏npm audit)** — 6 התראות high בספריית `sharp` (‏CVEs של libvips בפענוח תמונות), שמגיעה דרך `next`. **לא להריץ `npm audit fix --force`** — הוא היה מוריד את Next ל-v9 (הרס). משטח הסיכון אצלנו נמוך: המדיה נשמרת ומוגשת דרך R2 (‏presigned URLs), לא דרך אופטימיזציית התמונות של Next שמשתמשת ב-sharp; ו-`sharp` בעיקר משמש בבניית האייקונים (קלט מהימן — ה-SVG שלנו). תיקון נכון אם נרצה: `overrides` שמכריח `sharp@^0.35.0` בלי לגעת ב-Next — דורש אימות שהבנייה עומדת בו. **החלטה נדרשת ממך** לפני/אחרי הפריסה.
3. **אימותי קצה תלויי-פריסה** — מייל אמיתי, לחיצת `wa.me` מהטלפון, קבלן שפותח קישור קסם מהנייד. בלתי-אפשריים מ-localhost. מכוסים ב-checklist §4.8.
4. **QA פיזי** — מכשיר אמיתי בתנאי שטח. ידני, תלוי פריסה.
